Model configuration

Closure uses your own model services and allowance. The public version supports OpenAI- and Anthropic-compatible endpoints, plus an Antigravity CLI channel. Providers differ in fields, capabilities, and billing.

Connect one working model first

Section titled “Connect one working model first”
  1. Add a provider and endpoint in model settings, using the API key supplied by that service.
  2. Check the base URL and model identifier against the provider’s documentation. A web-chat URL is not an API endpoint.
  3. Save and test the connection or send a short message. Confirm authentication, quota, and returned content.
  4. For image understanding, select a vision-capable model. Embedding, reranking, and image generation also need the appropriate capabilities; a familiar model name is not enough.

API keys are stored encrypted locally. Keep them out of Issues, screenshots, documentation, and public project files.

Assign models by task

Section titled “Assign models by task”

Planning, prose, review, research, and style analysis can use different models and reasoning settings. Complete one chapter with a stable setup before tuning quality and cost. Public v0.4.0 can save and switch entire assignment sets as presets.

Fallback models can take over after quota, authentication, timeout, or gateway errors, with the fallback source shown. Circuit breaking temporarily skips a repeatedly failing model and later probes for recovery. A successful fallback does not imply equivalent prose quality; review the result.

Usage and budgets

Section titled “Usage and budgets”

The usage page records local calls by model and task: tokens, latency, failures, and estimated costs. v0.4.0 adds soft and hard monthly budgets; reaching the hard cap blocks new calls. Estimates may differ from provider bills. If the retention window is shorter than a month, the monthly figure covers only retained records.

CLI channel and troubleshooting

Section titled “CLI channel and troubleshooting”

Antigravity CLI needs its own installation and login, followed by in-app configuration. Follow the connection and authorization messages. Tool capabilities change by release; note the differences between v0.3.2 and v0.4.0.

When a connection fails, check the URL, model name, credential, quota, and provider status. Add custom headers or request-body fields only when the service requires them. Online models, search, and imports send requests to their services: local storage does not mean inference never uses a network.

Sources: public README and v0.4.0 release.
